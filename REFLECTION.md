# Reflection: Kigali City Guide — Database, Models, and State Management

This document explains how the Firestore database was structured, how listings were modeled, how state management was implemented, and key design trade-offs and technical challenges encountered during development.

---

## 1. Firestore database structure

The app uses two top-level collections in Cloud Firestore.

### `listings` collection

- **Purpose:** Stores every place/POI (hospitals, restaurants, parks, etc.) that users can view and contribute.
- **Document ID:** Auto-generated by Firestore (`add()`) for new listings.
- **Fields per document:**

  | Field           | Type     | Description                                      |
  |----------------|----------|--------------------------------------------------|
  | `name`         | string   | Display name of the place                        |
  | `category`     | string   | One of: Hospital, Police Station, Library, Restaurant, Café, Park, Tourist Attraction |
  | `address`      | string   | Human-readable address                           |
  | `contactNumber`| string   | Phone or contact info                            |
  | `description`  | string   | Free-text description                            |
  | `latitude`     | number   | Latitude for map display                         |
  | `longitude`    | number   | Longitude for map display                        |
  | `createdBy`    | string   | Firebase Auth UID of the user who created it     |
  | `createdAt`    | timestamp| Set on create only, via `FieldValue.serverTimestamp()` |

- **Queries used:**
  - **All listings:** `listings` ordered by `createdAt` descending (newest first), via `.orderBy('createdAt', descending: true).snapshots()`.
  - **Current user's listings:** `listings` where `createdBy == uid`, then sorted by `createdAt` in the app (see trade-offs below).

There are no subcollections; everything is a single flat collection for simplicity.

### `users` collection

- **Purpose:** Store profile and app-specific user data in sync with Firebase Auth.
- **Document ID:** Firebase Auth `uid` (one document per user).
- **Fields per document:**

  | Field          | Type     | Description                                      |
  |----------------|----------|--------------------------------------------------|
  | `uid`          | string   | Same as document ID                              |
  | `email`        | string   | User's email                                     |
  | `fullName`     | string   | Display name (also set on Auth `displayName`)    |
  | `createdAt`    | timestamp| When the user signed up                          |
  | `emailVerified`| boolean  | Kept in sync with Auth's email verification      |

- **Usage:** Written on sign-up; `emailVerified` is updated when the user verifies their email so the app can show verified status or gate features if needed.

## 2. How listings were modeled

Listings are represented in Dart by a single **`Listing`** class in `lib/models/listing.dart`.

- **Properties:** `id` (optional, set from Firestore document ID), `name`, `category`, `address`, `contactNumber`, `description`, `latitude`, `longitude`, `createdBy`, and `createdAt` (optional `DateTime`).
- **Serialization:**
  - **From Firestore:** `Listing.fromFirestore(DocumentSnapshot doc)` reads the document ID and map, handles missing fields with defaults (e.g. empty strings, 0 for numbers), and converts the `createdAt` `Timestamp` to `DateTime`.
  - **To Firestore:** `toMap()` returns a map of all fields except `id` and `createdAt`. On **create**, the service adds `createdAt: FieldValue.serverTimestamp()`; on **update**, only the editable fields are sent (no `createdAt`), so the original timestamp is preserved.
- **Categories:** A fixed list `listingCategories` and a helper `getCategoryIcon(category)` live in the same file so the app and Firestore stay aligned on allowed category values.

This keeps one source of truth for the listing shape and makes it easy to add or change fields in one place (model + service + Firestore rules).

## 3. State management (Riverpod)

State management is done with **Flutter Riverpod**. The app is wrapped in `ProviderScope` in `main.dart`.

### Service layer

- **`authServiceProvider`** and **`listingServiceProvider`** are plain `Provider`s that expose singleton instances of `AuthService` and `ListingService`. All Firebase Auth and Firestore access goes through these services.

### Auth state

- **`authStateProvider`** is a `StreamProvider<User?>` that listens to `FirebaseAuth.instance.userChanges()`, so the UI reacts to sign-in, sign-out, and token changes.
- **`currentUserProvider`** is a `Provider<User?>` that derives the current user from `authStateProvider.value`, so screens can depend on "current user" without dealing with the stream directly.

### Listing state

- **`allListingsProvider`** is a `StreamProvider<List<Listing>>` that listens to `ListingService.getAllListings()`, i.e. the Firestore stream of all listings ordered by `createdAt`.
- **`userListingsProvider`** is a `StreamProvider<List<Listing>>` that depends on `currentUserProvider`: when the user changes, it listens to `getUserListings(uid)` for that user. This keeps "my listings" in sync with auth and Firestore.

### Routing / auth gating

In `main.dart`, **`AuthWrapper`** uses `authStateProvider` to decide the root screen:

- **Loading:** show a loading indicator.
- **Error:** show an error message.
- **Data:**
  - No user → **OnboardingScreen** (intro + sign-up / login).
  - User not email-verified → **EmailVerificationScreen**.
  - User signed in and verified → **HomeScreen** (tabs: Directory, Map, My Listings, Settings).

So auth state is the single driver for top-level navigation, and listing screens simply `ref.watch(allListingsProvider)` or `ref.watch(userListingsProvider)` for reactive, up-to-date data.

## 4. Design trade-offs and technical challenges

### Firestore indexing and sorting

- **All listings** use `orderBy('createdAt', descending: true)`, which requires a single-field index on `createdAt` (Firestore often creates it automatically).
- **User listings** are fetched with `where('createdBy', isEqualTo: uid)` and then **sorted by `createdAt` in the client**. Doing both `where` and `orderBy` in Firestore would require a composite index on `(createdBy, createdAt)`. Sorting in the app was chosen to avoid adding and maintaining that index while keeping "my listings" ordered by newest first. Trade-off: a bit more work and memory on the client; acceptable for moderate list sizes.

### Flat `listings` collection

- Listings are stored in one collection with no subcollections. This keeps reads and queries simple and avoids cross-collection logic. Trade-off: if the app later needs things like "reviews per listing" or heavy per-listing data, a subcollection (e.g. `listings/{id}/reviews`) might be better. For the current scope, a flat structure was the right fit.

### Email verification and `users` collection

- Requiring email verification before entering the app meant coordinating Auth (which knows `emailVerified`) with the app's routing. The `users` document stores `emailVerified` and is updated when the user verifies, so the app can rely on either Auth or Firestore for gating. Challenge: making sure the "verified" state is refreshed (e.g. after the user clicks the link) so the app doesn't leave them stuck on the verification screen; this is handled by reloading the user and, where needed, updating the Firestore `emailVerified` field.

### No pagination

- `getAllListings()` and `getUserListings()` return full streams of all matching documents. For a city guide with a bounded number of listings, this is acceptable. If the dataset grew large, introducing pagination (e.g. `limit()` + `startAfterDocument`) would be necessary to limit reads and UI load.

### Server timestamp only on create

- `createdAt` is set only when a listing is **created** (`FieldValue.serverTimestamp()`). Updates use `toMap()` without `createdAt`, so the creation time is never overwritten. This was an explicit choice to keep "created at" stable and avoid accidental changes.

### Reactive streams and no local cache

- Listing and auth state are fully reactive: the UI listens to Firestore and Auth streams and updates when data changes. There is no separate offline/cache layer in the app code; Firestore's own offline persistence can be enabled at the Firebase level if needed. The trade-off is simplicity vs. custom offline behavior.

---

## Summary

- **Firestore:** Two collections—`listings` (flat, with `createdBy` and `createdAt`) and `users` (profile + `emailVerified`), with minimal indexes and client-side sort for "my listings."
- **Listings:** One Dart model with Firestore (de)serialization, shared categories, and clear separation between create (with `createdAt`) and update.
- **State management:** Riverpod providers for services, auth stream, current user, and listing streams; `AuthWrapper` uses auth state to drive onboarding, email verification, and home.
- **Trade-offs:** Client-side sort for user listings to avoid composite index, flat collection for simplicity, no pagination (acceptable at current scale), and server timestamp only on create to preserve creation time.
